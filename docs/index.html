1  Mechanism under test

  • The cost. Opening a TCP connection blocks the application for one round trip — 50–200 ms on a long path, paid per connection.
  • The ClientNIC spoofs the SYN-ACK. It answers the client's SYN with an invented sequence number, so connect() returns in microseconds while the real SYN is still in flight. The invented number rides in the forwarded SYN's unused ack-number field, so the NICs need no side channel.
  • The ServerNIC reconciles. The server picks its own initial sequence number, so the ServerNIC subtracts the two to get a fixed offset, drops the real SYN-ACK, and rewrites seq/ack on every subsequent packet. Client data arriving before the offset is known is buffered per connection.
  • Four machines. Client and server run stock, unmodified TCP; the two middle machines run a custom DPDK data plane on vfio-pci-bound interfaces in user space.

2  Metrics and instrumentation

send_unlock
What
Client's SYN leaving the wire → client's first request byte leaving the wire. In plain TCP this is the window in which connect() has not returned and the application is blocked, so it equals one round trip.
Where
Client-side packet capture.
Why
The interval the spoofed SYN-ACK is built to collapse — the direct test of the mechanism.
flow completion time
What
First SYN → last packet of the connection.
Where
Client-side packet capture.
Why
The only number a user feels. Unblocking early is worth nothing if the reply lands at the same moment — this is where the buffering cost surfaces.
server_gap  (control)
What
Server's SYN-ACK going out → first request byte coming in.
Where
Server-side packet capture.
Why
It separates a genuine saving from a rearrangement: a large gap means the request was still travelling, a near-zero gap means it was already parked next door waiting.

Load generator

  • Custom asyncio generator, not iperf2. The workload is thousands of short connections; iperf2 gives each one an OS thread, which does not reach the 100,000-connection target. Each connection here is a task on one event loop, so the ceiling is file descriptors rather than threads.
  • Paced arrivals. Connection i starts at a fixed point on a clock and the achieved rate is reported, so a run that collapses into a burst is visible rather than mistaken for a latency result. Achieved rate matched the requested 500/s in every run.
  • The generator's clock is not trusted. Every number in this report comes from the endpoint packet captures; the generator's only timing role is starting connections, accurate to within 0.5 ms against a 100 ms effect.
  • Throughput is not measured. One 1 KB request per connection makes each flow a clean latency probe and leaves sustained transfer rate untested (§6).

3  Where the emulated delay is placed

  • All four VMs sit in one AWS VPC, ~1.5 ms apart, so the 50–200 ms effect must be emulated: each outgoing packet is held for a fixed delay before release.
  • The delay applies to packets leaving a machine, so the choice of machine decides which part of the path is modelled as long — and that decides the completion-time result.
  • Placing the whole delay on the server's egress gives a correct send_unlock but makes a completion-time gain arithmetically impossible: the server's SYN-ACK is the one packet the ServerNIC's buffer waits on, so delaying it delays the release by exactly the amount the spoof saved.
How the 100 ms is made: netem, 50 ms per side
loadgen → socket → TCP → qdisc (netem: hold 50 ms) → NIC → wire # run on each NIC VM's middle-leg interface (baseline stack) tc qdisc add dev $IF root netem delay 50ms limit 1000000
  • netem is a qdisc — the kernel's outbound scheduler. It timestamps each packet, parks it in a timer queue and releases it delay later. Pure waiting, one layer below TCP; nothing is looped back or rewritten.
  • 50 ms per side. A packet crosses the ClientNIC↔ServerNIC leg once each way and each NIC delays its own outbound side, so each holds NETEM_RTT_MS / 2. Both stacks read that one parameter, so they cannot drift apart.
  • limit 1000000 — netem's default 1000-packet queue would overflow at this delay and flow count, manufacturing loss the model never intended.
  • The DPDK stack cannot use tc: its middle-leg ports are bound to vfio-pci and invisible to the kernel. Both forwarders take --wan-delay-us=50000 instead — a timestamped FIFO on middle-leg TX, drained by the existing poll loop, computed from the same NETEM_RTT_MS.

The general condition: completion time improves only if the ServerNIC learns the sequence offset before the client's data would otherwise have arrived. All four endpoint placements fail it structurally, not by tuning.

Configuration measured here

  • Both endpoints carry no artificial delay. Client and server run a clean qdisc; the harness reads it back and fails the run if netem is attached to either.
  • The whole modelled distance sits on the ClientNIC↔ServerNIC leg — 50 ms held by each NIC on its own outbound side, via tc netem on the baseline stack and the in-forwarder queue on the DPDK stack.
  • The server's real SYN-ACK pays no emulated distance, matching the target topology: the server sits beside the ServerNIC, so its reply crosses one local hop and is dropped there by the translator. It never traverses the wide area.
  • The baseline runs under the identical delay model, from the same NETEM_RTT_MS parameter, so neither stack is advantaged.

Control: the server-side gap

  • Plain TCP: 101.5 ms. The server sends its SYN-ACK then waits a full round trip for the client's reply, so the gap is the round trip.
  • 0-RTT: 0.259 ms. The request had already crossed the distance during the handshake and was parked at the ServerNIC, reaching the server as soon as the offset was known — the buffering overlaps the journey rather than adding to it.

5  What the results establish

  • The application stops waiting a round trip early — 101.3 ms across 2000 connections, 99th percentile under half a millisecond. This follows directly from the spoofed SYN-ACK.
  • The connection also finishes a round trip earlier — 101.9 ms, holding through the median, 99th percentile and worst case. This is the claim the design could have failed: the ServerNIC's buffering is a real cost and could have consumed the whole saving. It does not, under the modelled topology.
  • Each NIC must sit beside its own endpoint. The ServerNIC's buffer releases only when the server's SYN-ACK arrives, so a ServerNIC↔server distance d costs 2 × d straight out of the saving — here d ≈ 0 (same LAN), so the buffer costs nothing. Symmetrically, a ClientNIC away from the client delays its spoofed SYN-ACK and nothing unblocks early.
  • Endpoint-side delay placement cancels the completion-time gain exactly (§3, Figure 2). Because the ServerNIC's release is gated on the server's SYN-ACK, any model that charges that one packet the modelled distance makes the buffer's cost equal the spoof's saving. This is a property of the measurement setup, not of the implementation.

6  Limitations and open questions

  • The distance is emulated. Constant delay, no jitter, reordering or loss; a real wide-area path has all four. A cross-region deployment is the natural next step.
  • Standard TCP extensions are disabled. Timestamps, SACK and window scaling are off, because the translator does not rewrite TCP options. Without SACK a lost segment has no fast-recovery path and waits for an RTO — so these results model production TCP only loosely.
  • Throughput is not measured. 1 KB per connection leaves sustained transfer rate through the translator untested. An earlier observation suggested per-connection throughput may be well below the kernel's; a design that saves a round trip but costs bandwidth is not obviously a win.
  • The run pair has been repeated eleven times. Twelve baseline runs and twelve 0-RTT runs across three deployments — 24,000 flows per stack — all passing every check, with the blocked-time mean varying by 1.27 ms on plain TCP and 0.22 ms on 0-RTT (§4). That is a measured distribution of run means, not a bound from two samples. It remains a distribution of means: a rare per-connection mode smaller than a run's own averaging would still be invisible, and every run shares one region, one instance type and one modelled RTT. Read the headline as "about one round trip".
  • Concurrency is lower than the load parameters suggest. The headline runs are 2000 connections in total, arriving at 500/s. With a mean flow completing in 203 ms (plain TCP) or 101 ms (0-RTT), that holds roughly 50–100 connections open at any instant, not 2000: the generator's 2000-connection concurrency cap never binds at this volume, because the run never has 2000 flows alive to cap. Sustained high concurrency is therefore untested, and is a separate question from the total-volume limit below.
  • Scale is not demonstrated, and both attempts have now failed. The results above are 2000 connections against a 100,000 target. Two 100k pairs have been run at 2000 conn/s. On 2026-08-11 plain TCP completed 100,000 of 100,000 while 0-RTT completed 84,143. On 2026-08-17 neither side completed: plain TCP managed 99,728 of 100,000 (272 failed) and 0-RTT 87,073 of 100,000 (12,927 failed). Both runs failed their endpoint metric check outright — 326 and 171 unresolvable metric events respectively — so the earlier "plain TCP completes 100k cleanly" reading does not replicate and should not be relied on. Latency at that load is not interpretable on either stack (plain TCP's 95th-percentile blocking time reached 64.1 s, which is queueing, not path). The 0-RTT shortfall is the larger and reproduces across both attempts; whether it is endpoint exhaustion or a data-plane limit is still unresolved. No figure in this report depends on it.

    This is scoped out rather than answered, and the scoping is deliberately narrow: the shortfall is not attributed to shared infrastructure. Under identical conditions the baseline lost 0.3 % of connections where 0-RTT lost 12.9 %, an asymmetry a common endpoint or harness ceiling would not produce. The claim made here is only that behaviour at 100k is not demonstrated, in either direction.
  • The reported arrival rate is not a measure of establishment. The generator derives "achieved conn/s" from how quickly it schedules its tasks, not from when connections actually opened — each task takes the concurrency semaphore after it is created, so the scheduling loop never feels backpressure. At the 2000-connection load the two agree, because nothing queues. At 100k they diverge sharply: scheduling finished in 50.000 s exactly on target while the run itself took 985 s, with a 99th-percentile time-to-first-byte of 31.7 s. Read the arrival rate as a requested ceiling that was met by the scheduler, never as evidence that connections were established at that rate.
  • A latency outlier is unexplained. An earlier run showed a small fraction of connections finishing several hundred ms late, consistent with a lost segment paying the minimum RTO. It did not recur here; a retransmission counter reading would settle it.
