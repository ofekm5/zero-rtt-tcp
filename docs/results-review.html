The four VMs

same hosts, two data planes

netem is the Linux kernel's network emulator, attached to an interface with tc as a queueing discipline: it holds every outgoing packet for a fixed time, and that held time is the distance. Client and server run the same application in both stacks and neither knows the middleboxes are there. The three test rounds each ran on their own set of four EC2 instances, created and torn down around the runs.

One connection, end to end

0-RTT stack, single 1 KB request
  1. Client sends the SYN.
  2. ClientNIC answers with a SYN-ACK of its own, using a made-up ISN. connect() returns here.
  3. ClientNIC forwards the SYN across the 50 ms leg, with the client's ISN stamped into the unused ack field.
  4. Client sends its ACK and the 1 KB request straight away, so the data crosses the leg behind the SYN rather than after a round trip.
  5. ServerNIC reads the stamp, records the flow, and hands the server a clean SYN.
  6. The request data arrives while the server is still handshaking, so ServerNIC holds it. The offset is not known yet.
  7. The server's real SYN-ACK comes back. ServerNIC works out offset = made-up ISN minus real ISN, then drops the SYN-ACK, because the client already had one.
  8. The held data goes to the server with its sequence numbers shifted by the offset.
  9. The server's reply travels back with its sequence numbers shifted the other way, and the client acks it.
  10. FIN and ACK in both directions get the same shift, then both NICs drop the flow entry.

How a run is produced

nine steps, then the same nine for the other stack

The orchestrator drives all four VMs over SSM. Both stacks run back to back on the same set of instances, and the load parameters are recorded per run and checked equal before the two are compared.

The load generator, and why not iperf

step 6

What iperf could not give us

  • One throughput figure per stream, and no per-connection timeline. The claim is about when a single connection unblocks, which iperf never reports.
  • A thread per connection, which cannot reach 500 arrivals a second on these endpoints.
  • All connections starting at once, so every flow's latency included queueing behind all the others. That measures the forwarder's SYN service rate, not the round trip.
  • A 1 MB default payload. With window scaling off that costs about sixteen round trips of transfer, which left the one saved RTT at a few percent of flow time, under the run-to-run noise.

What the Python generator does instead

  • asyncio, one coroutine per connection, so 500 arrivals a second costs no threads.
  • Connection i is scheduled at t0 + i/rate on an absolute timeline, so per-sleep overhead cannot drift over a long run.
  • It reports the arrival rate it actually achieved. A run that collapses into a burst shows up as a burst instead of passing for a latency result.
  • 1 KB per connection, one segment, so flow time is handshake plus one round trip and the saved RTT is the dominant term.
  • A concurrency ceiling bounds endpoint memory and file descriptors independently of the pacing.

Nothing is timed inside the load generator. The Python code never records a start or stop time that reaches a result. Every reported number is the difference between two tcpdump timestamps, and the generator's only job is to open connections. This is separate from the 100 ms of netem, which is delay we inject, not a measurement.
  • TTFB and FCT are both intervals inside the client's own capture, so a single clock produces both and no host-to-host time synchronisation is needed.
  • The server capture is used to confirm each flow completed, matched by 4-tuple. That is a count, not a timing, so the two clocks never have to agree.
  • Each pcap is parsed on the host that recorded it, then only the summary rows travel.
  • The captures cover the whole run and both stacks are captured the same way, so an artefact of the tooling would land on both sides.

Cloud condition

where the distance has to sit
The gain survives only if the ServerNIC learns the sequence offset before the client's data would have arrived anyway. The buffer releases on the real SYN-ACK, so anything that delays that SYN-ACK comes straight out of the saving.
  • Each NIC has to sit next to its own endpoint. A distance d between the ServerNIC and the server costs 2 × d out of the saving.
  • Putting the emulated delay on either endpoint fails as arithmetic, not as tuning. Charging the server's SYN-ACK the modelled distance delays the release by exactly what the spoof saved, whatever numbers you pick.
  • So the delay goes on each NIC's middle-leg egress, 50 ms per side, with both endpoints on a clean qdisc. The harness reads the qdiscs back before every run and refuses to continue if they are wrong.

The same 100 ms, moved one link

cloud condition

Both rows are the same four VMs carrying the same connection with the same 100 ms of netem. The only change is which link holds it. Read each row's timeline as one question: how long does the held data sit at the ServerNIC between arriving and becoming releasable? In (a) the ServerNIC has to fetch the server's SYN-ACK across the delayed link, so the offset lands a round trip after the data and the wait cancels the saving exactly. In (b) the SYN crosses the delayed link alongside the data and the server is a local hop away, so the offset is ready as the data arrives. Placement (a) stands for every arrangement that charges the server side of the chain, which is why the delay lives on the middle leg.

What is not demonstrated

limitations
  • The distance is emulated: constant delay, with no jitter, reordering or loss. One region, one instance type, one RTT value.
  • TCP options are off, because the translator does not rewrite them. Without SACK a lost segment waits for an RTO, so this models production TCP loosely.
  • Throughput is unmeasured. 1 KB per flow makes a clean latency probe and says nothing about sustained transfer. An earlier run suggested per-connection throughput sits below the kernel's.
  • Concurrency is roughly 50 to 100 open flows, not 2000: arrivals at 500/s with flows lasting 100 to 200 ms. Sustained high concurrency is untested.
  • 100k flows fails on both stacks. Plain TCP completed 99,728 and 0-RTT 87,073, and both failed their metric check. Blocking p95 reached 64 s, which is queueing rather than path.
  • The ceiling is in the SmartNICs. One busy-poll lcore drives both ports, and a 1024-deep RX ring drained 32 packets an iteration absorbs about 32 iterations of burst. A 100k burst overruns that: imissed hit 16,891 on the ServerNIC and 2,236 on the ClientNIC, while cycles per packet stayed 40 to 50 times under budget. A SYN dropped after the ClientNIC has already spoofed leaves the client believing it is connected and its data discarded. The fix is more RX queues or paced arrivals, not a faster loop.
Nothing in this deck depends on the 100k attempts. Behaviour at that scale is not demonstrated in either direction. The 12.9 % 0-RTT shortfall against 0.3 % on the baseline, under the same conditions, is still unexplained.

For discussion: what a paper needs

open decisions

Claim and framing

  • Is the contribution the mechanism or the placement condition? The placement result predicts where a middlebox like this can and cannot pay off, which may travel further than the implementation does.
  • How to position this against TCP Fast Open and QUIC 0-RTT. Both of those need endpoint changes and this does not. Is that the axis to argue on?
  • What is owed beyond measurement: an invariant on the offset translation, the RST, FIN and retransmission paths, and what happens when the real SYN-ACK never arrives.

Evidence still to gather

  • A real wide-area path, cross-region, with genuine jitter and loss instead of a constant emulated delay.
  • TCP options, at least SACK and window scaling. A reviewer will read their absence as modelling a TCP nobody runs.
  • Throughput and sustained concurrency as a second axis. A round trip saved at the cost of bandwidth is not obviously a win.
  • A root cause for the 12.9 % 0-RTT loss at 100k: endpoint exhaustion or the data plane. Either answer is publishable.
