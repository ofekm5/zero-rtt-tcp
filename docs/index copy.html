Zero-RTT TCP — measuring whether the handshake round trip can actually be removed

Experimental report · zero-rtt-tcp

Removing the TCP handshake round trip: does the middlebox actually make connections faster?

A pair of programmable SmartNICs can answer a client's SYN before the server has seen it, letting the application send data a full round trip early. Whether that also makes the connection finish sooner turns out to depend on a detail of how the network is modelled — and getting that detail wrong hid the result entirely.

1  The cost being attacked

Opening a TCP connection costs one round trip before a single byte of application data may be sent. On a long-distance path that is 50–200 ms of pure waiting, paid on every new connection, and it dominates short transfers: an HTTP request of a few kilobytes spends most of its life in the handshake rather than in transfer.

What connect() is, and why it matters here

connect() is the system call an application makes to open a TCP connection — the line of code behind every requests.get(), every database client, every browser fetch. The kernel sends a SYN, waits for the server's SYN-ACK, replies ACK, and only then does the call return.

Until it returns, the application is blocked: it holds the bytes it wants to send and cannot hand them to the socket, no matter how ready it is. That blocked window is exactly one network round trip, and it is the thing this project removes. The first metric in Section 3, send_unlock, is that window measured from the wire.

The idea tested here is to answer the client locally. A programmable NIC in front of the client recognises the SYN and immediately returns a forged SYN-ACK carrying a sequence number it invents, so the client's kernel finishes its handshake in microseconds while the real SYN is still crossing the network. The difficulty is what follows: the real server will later choose its own initial sequence number, which will not match the forged one, so every subsequent packet in both directions is wrong by a fixed offset and something must correct them transparently — without either endpoint being modified or able to tell.

2  How the two NICs divide the work

The chain is four machines. The client and server run stock, unmodified TCP; the two middle machines run a custom DPDK data plane with the network interfaces taken away from the kernel entirely, so packets are handled in user space at line rate.

The packet flow, in five steps

  • ClientNIC sees the SYN → invents an initial sequence number and answers the client with a forged SYN-ACK straight away.
  • ClientNIC forwards the same SYN onward, with that invented number written into the unused ack number field of its TCP header — so the SYN itself carries the information the far side needs, and the two NICs need no channel of their own.
  • ServerNIC reads and stores the invented number as the SYN passes, then lets the SYN continue to the server untouched.
  • The server's genuine SYN-ACK arrives at the ServerNIC → it subtracts the two numbers to get a fixed offset, and drops the SYN-ACK, since the client was answered long ago. From here it rewrites the ack number of every client-to-server packet and the sequence number of every server-to-client packet.
  • Client data that arrives before that offset is known is buffered per connection and released the moment it is. This buffer is the crux of the whole result: whether it costs anything depends entirely on whether the waiting overlaps something else useful.

3  What has to be measured, and with what

A single latency number cannot answer the question, because the design moves waiting from one place to another and a summary statistic hides the move. Three quantities are extracted independently, all from packet captures taken at the two endpoints — never from the traffic generator's own self-reporting.

Why the traffic generator was rewritten

Earlier runs used iperf2. It was replaced with a purpose-built asynchronous generator, for two reasons — plus one thing that was given up.

  1. The test is thousands of short connections, not a few long ones. iperf2 gives every connection its own operating-system thread. The target for this work is 100,000 connections at once, and no instance size runs 100,000 threads — it falls over on scheduling and memory before a single packet is sent. The replacement runs each connection as a lightweight task on one event loop, so the limit becomes open file descriptors instead of threads.

  2. Connections have to start on a schedule, not all at once. If they all start together, each one's time includes waiting in line behind the others — that measures how fast the middlebox can chew through a burst, not the round trip we are actually asking about. The replacement starts connection i at a fixed point on a clock and reports the rate it really achieved, so a run that collapses into a burst is visible rather than mistaken for a latency result.

  3. What that cost us — two downsides, one of which survives.

    Can you trust a tool we wrote ourselves? A well-known C benchmark is credible on its own; ours is not. But we never ask the generator what time anything happened. tcpdump runs on the client and on the server, and every number in this report is computed from those captures — from packets on the wire. If the generator's own clock were wrong, the results would not move. Its one real job is starting connections at the right moments, and it does that to within half a millisecond against a 100 ms effect. So this downside does not threaten the result.

    We stopped measuring throughput. Every connection now sends exactly one 1 KB request, so nothing here tells you how fast a large transfer moves through the translator. There is no defence for this one — it is a genuine hole, and Section 7 lists it as such.

4  Why the modelled network's geometry decides the answer

All four machines sit in one datacentre, a genuine round trip apart of roughly 1.5 ms. The effect under study is 50–200 ms, so distance must be simulated: the kernel is told to hold each outgoing packet for a fixed delay before releasing it to the hardware. The subtlety is that such a delay applies to packets leaving a given machine, so choosing which machine to slow down chooses which part of the path is modelled as long.

How the 100 ms is made: netem, 50 ms per side

Every interface has a qdisc — the kernel's outbound packet scheduler, the last thing a packet passes on its way to the NIC. netem is a qdisc that timestamps each packet, parks it in a timer queue, and releases it delay later. Nothing is looped back or rewritten, and the application cannot tell: it is pure waiting, inserted one layer below TCP.

loadgen → socket → TCP → qdisc (netem: hold 50 ms) → NIC → wire # run on each NIC VM's middle-leg interface (baseline stack) tc qdisc add dev $IF root netem delay 50ms limit 1000000
  • Where 50 ms comes from. NETEM_RTT_MS=100 is the round trip we want to model. A packet crosses the ClientNIC↔ServerNIC leg once in each direction, and each NIC delays its own outbound side, so each holds NETEM_RTT_MS / 2 = 50 ms. 50 ms out + 50 ms back = the 100 ms round trip. Both stacks read that single parameter, so they cannot drift apart.
  • Why any delay at all. The four VMs share one AWS VPC and are genuinely ~1.5 ms apart. The effect under study is 50–200 ms, so at the real distance the entire saving would be lost in noise.
  • Why limit 1000000. netem's default queue is 1000 packets; at this delay and this many parallel flows it would overflow and tail-drop, manufacturing packet loss the model never intended. The raised limit keeps it pure delay.
  • Why the DPDK stack cannot use it. Its middle-leg ports are bound to vfio-pci and invisible to the kernel, so tc cannot touch them. Both forwarders instead take --wan-delay-us=50000 — a timestamped FIFO on middle-leg TX, drained by the existing poll loop — computed from the same NETEM_RTT_MS by wan_delay_us().

An earlier configuration placed the entire delay on the server's outbound traffic. That is a defensible reading — the server is far away, so its replies take a long time — and it produces a correct send_unlock result. But it also makes a completion-time gain arithmetically impossible, and it took a careful look to see why.

Stated generally: completion time improves only if the ServerNIC learns the sequence offset before the client's data would otherwise have arrived. All four possible endpoint placements fail that condition, and the failure is structural rather than a matter of tuning.

This is not a convenient choice of parameter. The link between the two NICs is where the distance genuinely lies in the deployment the design targets — one NIC beside the client, one beside the server, and the wide area between them. The earlier configuration modelled the network incorrectly, and the baseline is measured under the identical model, so neither stack is advantaged.

What was actually changed

  • Both endpoints were stripped of all artificial delay. The client and the server now run with a clean qdisc, and the harness reads it back and fails the run if any netem is still attached to either of them.
  • The whole modelled distance moved onto the ClientNIC↔ServerNIC leg — 50 ms held by each NIC on its own outbound side, by tc netem on the baseline stack and by the in-forwarder queue on the DPDK stack.
  • The consequence for the SYN-ACK is the point of the whole exercise. The server's real SYN-ACK no longer pays any emulated distance: in the topology being modelled the server sits right next to the ServerNIC, so its reply crosses one local hop and is dropped there by the translator. It never travels the wide area at all. Charging it a full wide-area crossing — which is exactly what putting the delay on the server's egress did — was modelling a journey that this packet does not make, and it was the reason the offset always arrived one round trip late.
  • The 0-RTT logic itself was not touched. Forging, stamping, buffering and translating are the same code that produced the earlier flat result; what was added is the delay queue that models the wide area, and what changed is which link it sits on.

5  Results

Both stacks were run back to back with identical parameters: 2000 connections arriving at 500 per second across four ports, one kilobyte of request per connection, 100 ms of modelled round trip. Every connection succeeded on both stacks, and the achieved arrival rate matched the requested rate, so neither run degraded into a burst.

The control confirms the mechanism rather than a coincidence

The clearest evidence that the buffering genuinely overlaps the journey — rather than the saving arising some other way — is the server-side gap. In plain TCP the server sends its SYN-ACK and then waits a full round trip for the client to react and reply, so the gap is the round trip: 101.5 ms. Under 0-RTT the same gap is 0.259 ms. The request did not travel after the SYN-ACK; it was already waiting a few metres away, having crossed the distance during the handshake, and reached the server almost the instant the offset became known.

6  What this means for the goal

The project's aim was to remove one round trip from connection setup. Two distinct claims follow from that aim, and they are worth keeping apart because only one of them was ever in doubt.

  • The application stops waiting a round trip early. This follows directly from the forged SYN-ACK and was never seriously in question; it is confirmed here at 101.3 ms across 2000 connections, with the 99th percentile under half a millisecond.
  • The connection also finishes a round trip earlier. This is the claim that matters to a user, and it is the one the design could plausibly have failed — the server-side buffering is a real cost and could have consumed the entire saving. It does not: completion time falls by 101.9 ms, and the saving holds through the median, the 99th percentile and the worst case, not merely on average.
  • The ServerNIC has to be near the server. Not near the client — near the server. Mechanically:
    • The ServerNIC is holding the client's data, and cannot release it until it knows the sequence offset.
    • It learns that offset from the server's real SYN-ACK. So the release time is set by how long the server takes to answer — that is, by the ServerNIC↔server distance, call it d.
    • In this experiment d ≈ 0, since the two share a LAN. The client's data arrives at the ServerNIC at t = 50 ms, one WAN crossing; the SYN arrives at the same moment, the server replies instantly, and the SYN-ACK is back at t ≈ 50 ms. Both land together, so the buffer holds for ~0 and costs nothing.
    • Move the ServerNIC 20 ms away from the server and the SYN needs 20 ms more to reach it and the SYN-ACK 20 ms to come back: the offset is known at t = 90 ms, while the data has been sitting there since t = 50. The buffer now costs 2 × d = 40 ms, straight out of the saving.
    The same argument puts the ClientNIC beside the client — otherwise its forged SYN-ACK takes real time to come back and nothing unblocks early. Each NIC beside its own endpoint, the distance between them: quote the result with that condition attached.

The other result is about measurement, and it travels further

The implementation was correct the whole time. It was measured under a network model that looked perfectly reasonable — the server is far away, so make the server slow — and under that model the metric that mattered showed exactly zero benefit.

Nothing looked broken. Every check passed, all 2000 connections succeeded, the analysis code was fine. The number was simply flat — and a flat number reads as the idea does not work.

What had actually happened is that the model slowed down the one packet the design waits on. The ServerNIC releases its buffered data when the server's SYN-ACK arrives; the model had made that exact SYN-ACK pay the full modelled distance. So the time the forgery saved and the time the buffer spent waiting were the same time, and they cancelled.

No summary statistic can show you that. It only became visible by asking, metric by metric, which single packet decides this number? — and then checking whether the model had put a delay on that packet. That question is worth asking of any middlebox measurement.

7  Limitations and open questions

  • The distance is emulated, not real. The model applies constant delay with no jitter, reordering or loss. A real wide-area path has all four, and loss in particular interacts badly with this design — see the next point. A cross-region deployment is the natural next step.
  • Standard TCP extensions are disabled. Timestamps, selective acknowledgement and window scaling are switched off, because the translator does not rewrite TCP options and the endpoints must therefore not negotiate them. Without selective acknowledgement a single lost segment has no fast-recovery path and must wait for a retransmission timeout. This limits how closely the results model production TCP.
  • Throughput is not measured. Every connection carries one kilobyte, which makes each flow a clean latency probe but leaves sustained transfer rate through the translator untested. An earlier observation suggested per-connection throughput might be substantially below the kernel's, and that question remains open — a design that saves a round trip but costs bandwidth is not obviously a win.
  • The run pair has not been repeated. These numbers come from one baseline run and one 0-RTT run. The per-connection spread within them is small, but run-to-run variance is unmeasured, so the headline should be read as "about one round trip", not as three decimal places. Repeating the pair a handful of times is cheap and is the first thing to do.
  • Scale is not yet demonstrated. These results are 2000 connections. The target is 100,000, at which point the ability of a single forwarding core to absorb arrival bursts becomes the binding constraint rather than latency.
  • A latency outlier remains unexplained. An earlier run showed a small fraction of connections finishing several hundred milliseconds late, consistent with a lost segment paying the minimum retransmission timeout. It did not recur in these runs, but one clean run is not evidence of absence, and a single retransmission counter reading would settle it.
